# FlowForge Case Study Guidelines

## Purpose

Case Studies are the strongest proof of FlowForge's capabilities.

Their purpose is not to demonstrate coding skills.

Their purpose is to demonstrate how FlowForge solves real business problems.

Visitors should finish each Case Study with one impression:

"This product solves a real operational problem."

---

# General Principles

Every Case Study should tell a story.

Never present features without context.

Every Case Study should answer:

1.

What problem existed?

2.

How does FlowForge solve it?

3.

What does the product look like?

4.

What business value does it create?

---

# Standard Structure

Every Case Study should follow the same reading order.

## 1. Problem

Describe the real business pain.

Avoid technical language.

Visitors should immediately understand:

"What problem is being solved?"

---

## 2. Solution

Explain the workflow.

Prefer diagrams.

Avoid implementation details.

Focus on user flow.

---

## 3. Product Showcase

This is the most important section.

Large screenshots.

Minimal decoration.

Visitors should immediately recognize:

"This is a real enterprise system."

---

## 4. Key Capabilities

Explain:

How the product improves work.

Do not create long feature lists.

Prefer grouped capabilities.

Example:

Production Reporting

- Reporting
- Process Tracking
- Work Orders
- Real-time Status

Instead of:

- Add
- Edit
- Delete
- Search

---

## 5. Business Outcome

Summarize the result.

Examples:

- Faster reporting
- Reduced manual work
- Better visibility
- Standardized workflow

Business outcomes are more important than technical details.

---

# Product Showcase Principles

Product Showcase is the visual center of every Case Study.

Rules:

- Large product preview
- Minimal decorations
- High readability
- Realistic data
- Clear hierarchy

Avoid:

- Generic dashboard layouts
- Random KPI collections
- Placeholder data
- Decorative widgets

---

# Screenshot Guidelines

Screenshots should represent real usage.

Avoid:

- Empty tables
- Lorem ipsum
- Fake statistics
- Demonstration-only data

Whenever possible:

Use realistic manufacturing data.

---

# Product Preview Principles

Every Product Preview should answer one question.

"What is happening right now?"

Visitors should understand the current state within three seconds.

Structure:

Hero KPI

↓

Supporting Information

↓

Recent Activity

Only one Hero KPI.

Everything else supports it.

---

# Product Personality

Each product should have its own personality.

Never create three products that look like different versions of the same dashboard.

---

## Production Reporting

Core message:

Production is moving.

Visual focus:

- Progress
- Work Order
- Process
- Current Status

Hero KPI examples:

- Completion Rate
- Current Output
- Today's Production

Supporting Information:

- Work Order
- Product
- Process
- Quantity

Recent Activity:

Latest reporting event.

Visitors should immediately understand:

Current production progress.

---

Inventory is under control.

- Difference Count
- Inventory Completion
- Available Stock

Supporting Information:

- Warehouse
- Item
- Location

Latest inventory movement.

Current inventory condition.

---

Issues are being tracked and resolved.

Visual focus:

---

# Information Hierarchy

Never give every piece of information equal emphasis.

Priority:

1.

Hero KPI

2.

Product Status

3.

Supporting Information

4.

Recent Activity

5.

Decorative Elements

---

# Mobile Case Study

Desktop and Mobile are different experiences.

Do not simply shrink desktop layouts.

Mobile reading order:

Product Showcase

↓

Headline

↓

Description

↓

Capabilities

↓

Business Outcome

The Product Showcase should remain the visual focus.

Reduce secondary information if necessary.

Do not reduce the Hero KPI.

---

# Desktop Experience

Desktop should emphasize:

- Product credibility
- Visual rhythm
- Large screenshots
- Comfortable whitespace

Avoid making desktop pages resemble admin dashboards.

---

# Mobile Experience

On mobile:

Prioritize:

- Reading speed
- Touch interaction
- Product understanding

If necessary:

- Collapse secondary information
- Stack layouts vertically
- Hide non-critical metadata

Do not overwhelm users with excessive scrolling.

---

# Design Review Checklist

Before completing any Case Study, verify:

## Business

- Is the problem clearly explained?
- Is the business value obvious?

## Product

- Does the product look real?
- Is the preview believable?

## Visual

- Is there one visual focus?
- Is hierarchy clear?

## Desktop

- Comfortable spacing
- Large preview
- Clear rhythm

## Mobile

- Easy to read
- Preview remains dominant
- No horizontal scrolling
- Reasonable scrolling length

---

# Success Criteria

A successful Case Study should make visitors think:

"This is a production-ready enterprise product."

Not:

"This is a coding project."

Enterprise customers should understand the business value before noticing the technology.
